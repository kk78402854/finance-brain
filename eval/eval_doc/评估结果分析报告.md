## 四、根因分析

### 4.1 faithfulness 0.466：不是幻觉，是"合规模板污染"

RAGAS 忠实度的判定逻辑：把答案拆成陈述句，逐句验证能否由检索上下文支撑。以第 1 条（GDP）为例拆解：

```
✅ 可验证事实（约 30%）：
   "2025年全年GDP同比增长5.0%"          ← 上下文明确支撑
   "与政府工作报告5%左右目标一致"         ← 上下文支撑

❌ 无支撑文本（约 70%）：
   "**来源信息**：《中国货币政策执行报告》、政府工作报告（2025年）"
   "**内容类型**：宏观经济数据"
   "⚠️ 温馨提示：以上数据为官方初步核算结果，可能随后续统计调整..."
   "--- **风险提示**：金融产品存在风险，历史业绩不代表未来表现..."
```

这些来源标注、温馨提示、风险提示是**提示词模板固定生成的**，不来自检索上下文，被 RAGAS 判为"无支撑陈述"——但它们恰恰是金融场景的合规刚需。**本质矛盾：面向监管的合规冗余 vs 面向评估的事实纯净。**

### 4.2 answer_correctness 0.524：数值对，但被稀释 + 参考答案过短

两个叠加因素：
1. RAGAS 的 correctness = 事实相似度（0.6 权重）+ faithfulness（0.4 权重）——faithfulness 0.466 直接拖累约 0.2 分
2. 参考答案是单句（"同比增长5%"），系统答案是"数值 + 来源 + 双重提示"一大段，事实对齐得分被冗余文本稀释

### 4.3 context_precision 0.82：数值型问题的首位排序

第 5 条（汇率收盘价）precision 仅 0.583：含收盘价 6.9890 的"内容摘要" chunk 排在第二位，排首位的是"汇率制度"章节（讲中间价 7.0288，不含答案）。**数值型问题的精确值 chunk 排序偏低。** 另外 2 条 NaN 是裁判模型输出解析失败（RAGAS 单条容错跳过），属评估噪声，不影响结论方向。

### 4.4 运行期"报错"说明（均为无害噪音）

| 现象 | 原因 | 影响 |
|---|---|---|
| `Bad file descriptor` 刷屏 | 命令超时转后台时终端关闭日志文件句柄，loguru 写文件失败 | 仅日志落盘失败，评估正常完成 |

## 五、优化策略（按优先级）

### P0 生成层：答案正文与合规模板分离（预期收益最大）

**思路：让 answer 文本只含可验证事实，把合规内容移出正文。**

改造 [node_answer_output.py](../../../processor/query_processor/nodes/node_answer_output.py) 的答案提示词，输出结构改为：

```
【回答】仅基于上下文的事实性回答，1~3 句，禁止任何提示/免责/来源说明
【来源】引用的 chunk 标题列表（结构化字段，不进 answer）
【提示】风险提示模板（结构化字段，由前端渲染）
```

配套：state 新增 `sources` / `disclaimer` 字段，answer 只存【回答】部分；前端聊天页从新字段渲染来源和免责区块。

**预期**：faithfulness 0.47 → 0.85+（正文全部可验证），correctness 0.52 → 0.75+（对齐简洁参考答案），且合规能力不降反升（模板内容结构化后更规范）。

> 备注：若不想动前后端，最小改动是提示词加一句"回答后的来源与风险提示用 `<ctx-meta>...</ctx-meta>` 包裹"，评估脚本解析时剥离该标签——收益打八折，但当天可上线。

### P1 检索层：数值型问题的排序修正

- 第 5 条的病灶是"精确数值 chunk 排第二"。可尝试：
  - rerank 阶段对含表格的 chunk 提示词强调"数值精确匹配优先"
  - 或在 query 改写时把数值实体（"收盘价 6.9890"类问题的目标字段）显式化，提高含答案 chunk 的相关性得分
- 优先级低：recall 已满分，precision 0.82 的损失主要发生在"答案其实都在，只是首位不对"

### P2 评估层：扩大评估集 + 提升参考答案质量

当前 N=5 单文档，结论只能定方向，不能当基准线。建议：

1. `eval_doc/` 再放入 3~5 篇不同类型文档（基金合同、招募说明书、风险揭示书、FAQ），`python eval/gen_evalset.py --num 6` 扩到 30+ 条
2. 生成评估集的提示词追加要求："answer 用 2~3 句完整表述，包含关键数值及其背景"——避免单句参考答案天然压低 correctness
3. 修复后重跑 `python eval/evaluate_ragas.py`，与本次数据形成前后对比（这正是简历/面试里"评估驱动优化"的完整故事）

## 六、本次评估的元教训

1. **先验证评估链路本身，再解读指标**——首轮 contexts 全空导致三项指标归零，若直接解读会得出"知识库崩溃"的错误结论（本次根因：文档字段名 `text` 而非 `content`）
2. **指标低 ≠ 系统差**——faithfulness 0.47 的真凶是合规模板，是产品决策而非模型缺陷；评估报告必须区分"真缺陷"和"评估口径副作用"
3. **小样本只定方向**——N=5 的结论用于验证优化假设，基准线必须 30+ 条

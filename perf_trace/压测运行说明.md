# Locust 压测运行说明（finance-brain 查询服务）

- 压测对象：`api/query_service.py`，实际端口 **8002**（参考文档写的 8001 是错的）
- 压测脚本：`perf_trace/locustfile.py`
- 与参考文档第 4 章的差异（均按本项目真实接口实现）：
  - `/query` 返回体只有 `session_id`，**没有 `task_id`**（文档脚本会 KeyError）
  - SSE 事件名以 `utils/sse_utils.py` 为准：`ready / progress / delta / final / error`
  - 额外覆盖了非流式任务（文档只压了流式）

## 1. 前置条件

1. 虚拟机（192.168.10.8）上 Milvus / Mongo 正常（冒烟时实测 19530、27017 均可达）。
2. `.env` 中 Langfuse 三项配置齐全（`LANGFUSE_BASE_URL/PUBLIC_KEY/SECRET_KEY`），
   且 `http://192.168.10.8:3000` 可访问。**Langfuse 没启动时压测照常能跑，
   但 trace 不会上报**，服务日志会刷 `Failed to export spans batch`，SDK 重试耗尽后直接丢弃，
   事后补启动 Langfuse 也找不回这批 trace，只能重跑压测。
3. 启动查询服务（仓库根目录，另开一个终端）：

   ```powershell
   .\.venv\Scripts\python.exe api\query_service.py
   ```

   验证：浏览器或 curl 访问 `http://localhost:8002/health` 返回 `{"ok":true}`。

## 2. 冒烟（headless，不开 UI）

```powershell
.\.venv\Scripts\locust.exe -f perf_trace\locustfile.py --host http://localhost:8002 --headless -u 2 -r 1 -t 180s --stop-timeout 190 --only-summary
```

注意：
- 单次完整回答 25~40s，`-t` 不要低于 2~3 分钟，否则一个完整样本都拿不到；
- `--stop-timeout 190` 让停机时在途请求跑完再退出，避免统计被截断（不带它最后一轮请求会凭空消失）。

## 3. 正式压测（Web UI）

```powershell
.\.venv\Scripts\locust.exe -f perf_trace\locustfile.py --host http://localhost:8002 --stop-timeout 190 --web-port 8089
```

浏览器打开 http://localhost:8089，建议阶梯加压：**5 → 10 → 20 用户**，
spawn rate 1~2 用户/s，每档跑 5 分钟左右，观察失败率与 P95 再加下一档。

## 4. 统计口径（Statistics 每行含义）

| 行 | 含义 |
|---|---|
| `01 submit /query [流式]` | 提交流式任务，仅接口往返耗时（不代表回答完成） |
| `02 first answer delta` | 首段答案延迟：提交 → 首个非空 delta（自定义指标） |
| `03 complete answer [流式]` | 整链路耗时：提交 → 收到 final（含失败轮次） |
| `04 complete answer [非流式]` | 非流式整链路耗时：POST /query 同步等 answer |

任务权重：非流式 2 : 流式 3（约 40% / 60%）；问题从 6 题基金问题池随机抽取；
每个请求独立 session（模拟新对话，避免历史消息导致时延漂移）。

可用环境变量调整（均有默认值）：
`LOCUST_WAIT_MIN / LOCUST_WAIT_MAX`（用户思考时间）、
`LOCUST_QUERY_TIMEOUT`（单请求兜底超时）、`LOCUST_STREAM_DEADLINE`（等 final 的兜底时长）。

## 5. 压测结束后看 Langfuse

Langfuse SDK 是异步批量上报：**压测结束后等 30~60 秒再刷新页面**。

控制台 `http://192.168.10.8:3000` → 对应项目 → Tracing，按 `finance-query-api` 过滤。重点盯：

- trace 条数 ≈ 压测请求数（对账，防止静默丢上报）
- `node_rerank` / `node_web_search_mcp` / `node_answer_output` 的耗时分布（P95）
- generation 的 input/output token（每请求消耗，基线约 3.4k/334）
- `level=ERROR` 的 trace（失败归因，配合 Locust 的失败行看）

## 6. 常见故障：100% 失败、耗时集中在 4 秒、响应体 0 字节

**这是查询服务没启动**，不是业务超时，也不是脚本 timeout。

- 现象：`01 submit` 与 `04 complete answer [非流式]` 两行全失败，耗时挤在 4000~4100ms，`# bytes` 为 0；
  且不会出现 `02 first answer delta` / `03 complete answer [流式]` 这两行。
- 原因：Windows 上连接一个没人监听的本机端口，requests 要重试到约 4.1s 才抛
  `ConnectionError ... [WinError 10061] 由于目标计算机积极拒绝`。请求连 TCP 都没建立，
  自然没有业务执行，也不会有 Langfuse trace。
- 自查：`Invoke-WebRequest http://localhost:8002/health` 应返回 `{"ok":true}`；
  或看 Locust 的 Failures 页，异常信息就是 WinError 10061。
- 处理：另开终端 `python api/query_service.py`，约 25s 启动完成、/health 通了再压。
  脚本开跑前会自动请求 `/health` 并打印 `[precheck]`，连不上会直接提示启动命令。

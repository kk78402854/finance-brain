## 5. 失败分析（HTML Failures 页原始记录）

| 错误 | 任务 | 次数 | 首次出现 | 末次出现 |
|---|---|---|---|---|
| `CatchResponseError('HTTP 0: ')` | `04 非流式` | 33 | 18:54:37.95 | 18:55:23.52 |
| `CatchResponseError('提交失败 HTTP 0: ')` | `01 submit` | 45 | 18:54:43.21 | 18:55:24.39 |
| `读取 SSE 失败: ConnectionResetError(10054, '远程主机强迫关闭了一个现有的连接。')` | `03 流式` | 5 | 18:54:37.95 | 18:54:37.95 |

三条结论：

1. **`HTTP 0` 不是 4xx/5xx，而是"根本没收到 HTTP 响应"**——连接层面就失败了。这与上一轮验证过的签名完全一致：Windows 上连一个无人监听的端口，requests 重试到 ~4.1 s 抛 WinError 10061，所以这一簇耗时整齐地落在 4000–4100 ms。
2. **5 次 `ConnectionReset` 全部集中在 18:54:37.95 这一瞬间**——正是进程死亡的时刻，在途的 SSE 连接被强制掐断。这批请求的平均耗时 82 s，即"等了 82 秒后被重置"。
3. **失败起点 18:54:37.95，晚于服务日志最后一条业务记录 18:54:31（`node_rerank` 步骤完成 3635 ms），早于进程退出**——完整对上"进程在 18:54:31 之后几秒内崩溃"。

### 崩溃根因（进程日志 + 系统内存）

```
... ThreadPoolExecutor-23_0 / -23_1 ...（第 23 个线程池）
memory allocation of 17301520 bytes failed
```

- 退出码 `-1073740791`（0xC0000409），Windows 上的进程致命错误/内存分配失败。
- 主机总内存 **15.7 GB**，压测结束时仅剩 **1.8 GB**（此时服务进程已死）。
- 判定：**容量问题（内存耗尽）**，不是脚本问题（脚本超时 180 s/30 s 一次都没触发），也不是网络问题（Milvus/Mongo 全程正常）。

## 6. 三行失败逐行拆解（01 / 03 / 04）

先纠正一个常见误读：**这三行都不是严格的 100% 失败**，而是"几乎全是失败"，且原因同一个。

| 行 | 请求 | 失败 | 失败率 | 错误类型 | 失败时间窗 |
|---|---|---|---|---|---|
| `01 submit /query [流式]` | 51 | 45 | 88.2% | `提交失败 HTTP 0: `（无 HTTP 响应） | 18:54:43 → 18:55:24 |
| `03 complete answer [流式]` | 6 | 5 | 83.3% | `ConnectionResetError(10054)` | **全部 18:54:37.95** |
| `04 complete answer [非流式]` | 35 | 33 | 94.3% | `HTTP 0: `（无 HTTP 响应） | 18:54:37 → 18:55:23 |
| `02 first answer delta` | 3 | 0 | 0% | — | — |

**逐行解释**

- **`01`（提交）**：45 次失败全部发生在 18:54:43 之后，即崩溃之后。`HTTP 0` 表示连 HTTP 响应都没拿到，所以耗时整齐落在 4 秒（Windows 连接被拒的请求重试窗口）。崩溃前提交是成功的——这一行有 6 次成功记录（响应体积合计约 480 B）。
- **`03`（流式完整）**：请求数只有 6，是因为**提交失败的 45 次根本不会走到 `/stream`**；这 6 次里有 5 次正在等 final 时被进程崩溃掐断，`ConnectionReset` 时间戳精确重合在 18:54:37.95 这一瞬间，平均已经等了 82 秒。
- **`04`（非流式）**：33 次失败同样始于崩溃时刻，崩溃前只有 2 次真正拿到完整答案（33–86 s）。
- **`02` 的 0% 是幸存者偏差，不是健康证明**：它是自定义指标，**只在收到首个非空 delta 时才打点**；6 次流式里有 3 次连首 token 都没等到就断了，这些请求根本不会出现在这一行。所以"02 零失败"实际含义是"走到首 token 的那 3 次都成功了"，不能反推成功率。

**任务依赖形成的漏斗**

```
01 提交 51 次 ──成功 6 次──▶ 03 流式 6 次 ──收到首 delta 3 次──▶ 02 首段 3 次
   └─失败 45 次（不再发起 /stream）        └─3 次未到首 token 就断
```

行与行之间不是并列关系，而是**逐步收窄的漏斗**：上一环节失败会直接跳过后续环节，所以请求数从 51 → 6 → 3 递减。把这理解成"某个接口单独出问题"会误判——三行的失败都指向同一个事件。

**失败为何全部集中在崩溃后**：`fail/s` 在 18:54:39 之前一直是 0，所有 failure 的 `first_seen` 均 ≥ 18:54:37.95。也就是说本轮不存在"偶发失败/超时"，只有"服务整体消失"这一种失败模式。

## 7. 硬件与容量前提

**实测环境**

| 项 | 值 | 来源 |
|---|---|---|
| 显卡 | RTX 3060 Laptop，6 GB 显存 | 用户提供 |
| 内存 | 15.7 GB（压测结束时剩余 1.8 GB） | 本机实测 |
| 部署形态 | 压测端（Locust）与被压服务**同机** | 实际运行方式 |
| rerank 模型 | `bge-reranker-large`，`device=cpu`、`fp16=False`（fp32） | 配置读取 |
| 向量化模型 | `BGE-M3`，`device=cpu`、`fp16=False` | 配置读取 |
| LLM | qwen-flash 远端接口，单请求 3 次调用（约 3.4k 输入 / 334 输出 token） | 此前 trace |
| 依赖服务 | Milvus / Mongo 在虚拟机，不占本机内存 | 实际部署 |

**每个请求的固定开销构成**：本地 fp32 的 rerank（约 5.6 亿参数级）+ 本地 BGE-M3 向量化 + 数十条候选做 cross-encoder 逐对打分 + 3 次 LLM 往返 + 联网检索。这些是链路固有成本，不随并发数摊薄——10 个请求同时进来，就是 10 份并行打分上下文同时驻留在同一个 Python 进程里。

因此：**在 15.7 GB 内存、CPU 推理的单机配置下，承载上限落在个位数并发，属于硬件约束**，不应把"10 并发打满"当作该环境的设计目标。

**但必须把两件事分开说：硬件决定"上限"，设计决定"崩溃方式"。**

| | 硬件约束（无法靠改代码消除） | 工程缺陷（与硬件无关，可修） |
|---|---|---|
| 表现 | 并发个位数即接近内存天花板 | 没有并发闸门：`sync def` 路由 + FastAPI 线程池默认几十线程，10 个请求会同时进入重计算 |
| 表现 | 单请求 20 s 量级、rerank 占一半 | 没有内存上限与降级：OOM 时**整个进程被杀**，而不是对超额请求返回 503 |
| 表现 | 换更强的机器只能把数字推高一点 | 没有优雅退出/在途保护：5 条 SSE 被硬切断，客户端只看到 `ConnectionReset` |

换句话说：**换一台 64 GB 的机器，同样的设计只会把崩溃点从 10 并发推到更高并发，崩溃方式不变**。本轮 87.4% 的失败率、18:54:37 的进程崩溃都是既成事实，不会因为"硬件有限"而被解释掉——硬件解释的是"为什么上限这么低"，不是"为什么失败率这么高"。真正的健壮性问题在于：容量耗尽时系统没有任何缓冲，直接以"进程消失 + 在途请求全丢"的方式失败，这对线上是不可接受的降级形态。

> 需确认：本轮 rerank/embedding 均配置为 CPU 推理、LLM 走远端接口，**6 GB 显存在该链路中是否实际参与计算需要核实**；若后续把 LLM 或 rerank 改到本地 GPU，显存会成为比内存更紧的约束。

## 8. 结论与优化建议

单请求的时间结构（来自此前 trace 分析，1 用户）：**rerank 16.4 s（50.75%）+ 主体确认 7.1 s（21.9%）+ 联网检索 4.9 s（15.1%）+ 答案生成 2.4 s（7.6%）**，首段延迟 ≈ rerank 结束时刻。

按对吞吐的收益排序：

1. **先解决内存与并发上限，这是本轮唯一的硬阻断**
   - 用 `--limit-concurrency` 或应用层信号量把同时执行的图压到 4 以内先跑稳；
   - 每个请求持有的检索上下文/rerank 输入在节点结束即释放，不要挂在线程池里太久；
   - rerank 改成单实例固定 batch 队列，避免 20 个请求各自加载。
   - 验证：10 并发跑 5 分钟进程不退出、内存稳定在 70% 以下。

2. **压 rerank 的 16.4 s（单请求一半，也是并发时 CPU 抢光的元凶）**
   - 减少候选数/截断长度、rerank 服务化批处理、或换 ONNX/GPU。
   - 预期：首段延迟从 19 s 量级降到 10 s 量级，10 并发下的排队也同步缓解。
   - 验证：Langfuse `node_rerank` p95 + `02 first answer delta` p95。

3. **把联网检索的 4.9 s 加超时/按需触发**（此前 trace 已证明它的结果常未被答案引用）
   - 验证：`node_web_search_mcp` p95、`reranked_docs` 中 `type=web` 占比。

4. **下一轮压测参数**
   - 并发阶梯 **3 → 5 → 8**（每档 5 分钟），spawn rate 1/s，不要一步跳到 10；
   - 必开 `--csv-full-history`（本轮 HTML 曲线可看，但 CSV 侧无法复核趋势）；
   - 压测时同步记录服务进程内存（`Get-Process python | select WorkingSet`），把内存 80% 作为停止加压的硬指标；
   - 压测端与被压端尽量分机（本轮同机，且 Locust 自身也吃内存，崩溃可能有它的贡献）；
   - 判定标准：`fail/s` 必须为 0 的档位才算"稳定档"，`current_rps` 连续三档不再上升即为吞吐上限。

## 9. 本轮压测的局限

1. **只有一档并发（10 用户）**，没有 3/5/8 的对照，拐点只能给"10 已超载"，给不出精确承载力数值。
2. **样本极小**：完整答案仅 3 个（流式 1、非流式 2），`02 首段` 只有 3 个样本，分位数基本没有统计意义，只能当"量级"看。
3. **压测端与被压端同机**：共享 15.7 GB 内存与同一批 CPU 核，Locust 本身就是内存大户，崩溃可能被放大；绝对数值偏悲观，结论适用于"相对比较"。
4. **失败发生在崩溃之后，成功样本集中在崩溃之前**：所以"延迟 4 倍劣化"其实是崩溃前的表现，而"87.4% 失败率"是崩溃后的表现，两者不能合成一句话概括，本报告已分段表述。
5. **无 trace 级归因**：Langfuse 公共 API 返回 404，未能拿到并发下的节点耗时；rerank 占比沿用单用户基线推算。
6. **无 token / 成本 / 内存细分**：报告不含 token 与内存曲线；BGE-M3 与 reranker 各自占用多少内存属"需补充"。
7. **`total_avg_response_time` 是累计平均**，肉眼容易误读为瞬时恶化速度，本报告已改用时序分位列。
